### Cross-cutting theme — filesystem boundary (7 security findings)

The project's core invariant is "every write/delete stays under `~/.claude` (or, for project agents/skills, under `$HOME`)". The audit found the invariant is enforced **inconsistently**:

- **🟠 High** `electron/modules/agents-writer.ts:50-63` — createAgent/createSkill write outside ~/.claude (and outside $HOME) via unvalidated renderer projectPath
- **🟠 High** `electron/modules/plans-reader.ts:69-71,100-120` — Plan file content is read from an unconfined absolute path taken verbatim from the transcript (arbitrary file read, escapes the ~/.claude invariant)
- **🟡 Medium** `electron/main.ts:1100-1134` — sendMessage passes unvalidated sessionId to the SDK as `resume` (no isValidSessionId guard)
- **🟡 Medium** `electron/main.ts:396-428` — markdownFile:write / markdownFile:delete confined to $HOME, not ~/.claude — arbitrary .md overwrite/delete anywhere under home
- **🟡 Medium** `electron/utils.ts:32-38` — Path guards are purely lexical — no symlink resolution, so a planted symlink escapes ~/.claude/$HOME
- **⚪ Low** `src/components/project/chat/export.ts:201` — Unescaped tool name injected into raw <summary> HTML in the Audit Markdown export
- **⚪ Low** `electron/main.ts:124-147` — Path guards (assertSafeWritePath, deleteSessionArtifacts) don't resolve symlinks

Common root causes: (a) path guards are *lexical* (`path.resolve`, not `fs.realpathSync`) so symlinks aren't resolved; (b) some entry points (`agents:create`/`skills:create`, plan-file reads) skip the guard that siblings apply; (c) `markdownFile:*` confines to `$HOME` rather than `~/.claude`, widening the blast radius to any `.md` under home.

## 🟠 High priority (4)

_Re-verified by hand against the source._

#### 1. Aggregated project tokens are priced entirely at the single dominant model's rate, mispricing mixed-model projects

- **Severity:** 🟠 High · **Category:** correctness · **Cluster:** `cost-parsing`
- **Location:** `electron/modules/cost-tracker.ts:328-348`
- **Problem:** aggregateProject() sums input/output/cacheWrite/cacheRead tokens across all session files (lines 333-340), then computes a single cost by pricing that grand total at the rate of ONE model only -- the dominantModel, chosen by counting how many *files* use each model (line 339), not by token volume. A project where a single huge Opus session dominates token volume can still be billed entirely at Sonnet/Haiku if there happen to be more files of the other model; conversely two trivial Opus files plus one massive Haiku session prices all the Haiku tokens at Opus (exactly what the test at lines 255-272 enshrines: 1,000,020 tokens, ~1M of them Haiku, all priced at Opus). This is a coarser model than parseJsonlSession uses per session: getSessionList (lines 400-402) prices each session at that session's own dominant model, so the per-session list and the project rollup can show materially different totals for the same data.
- **Impact:** Project-level cost figures and the cost-summary ranking (calculateCostSummary) can be wrong by up to roughly 5x-19x in either direction for any project that mixes Opus/Sonnet/Haiku (common: Haiku for subagents/titles, Opus/Sonnet for main work). Users comparing projects or trusting the dollar amount get a misleading number that silently contradicts the per-session breakdown.
- **Fix:** Price per-session (each session already knows its own dominant model) and sum the resulting dollar costs in aggregateProject -- i.e. accumulate `cost += calculateCost(s.inputTokens, s.outputTokens, s.cacheWriteTokens, s.cacheReadTokens, s.model)` in the loop -- instead of summing tokens across models and applying one rate. If a single display model is still needed, weight the dominant-model pick by token volume rather than file count, and update the test at lines 255-272 accordingly.

#### 2. createAgent/createSkill write outside ~/.claude (and outside $HOME) via unvalidated renderer projectPath

- **Severity:** 🟠 High · **Category:** security · **Cluster:** `filesystem-security`
- **Location:** `electron/modules/agents-writer.ts:50-63`
- **Problem:** agents:create / skills:create pass the renderer-supplied projectPath straight into the write-path base with no validation. createAgent builds agentsDir = join(projectPath ? join(projectPath, '.claude') : CLAUDE_DIR, 'agents') and then assertWithin(agentsDir, filePath). The only containment check is that the filename stays under agentsDir — but agentsDir itself is derived from the attacker-controlled projectPath, so assertWithin always passes regardless of where projectPath points. createSkill (skills-writer.ts:37-50) is identical: skillsDir = join(projectPath, '.claude', 'skills'), assertWithin(skillsDir, skillDir). The name is validated (validateEntityName rejects separators and '.'/'..'), but the directory prefix is not. The IPC handlers (main.ts:716-732) forward projectPath with no assertValidHash/assertSafeWritePath. preload.ts:104/109 expose create(input, projectPath) directly. The renderer normally passes project.realPath, but the main process must treat IPC input as untrusted (cf. the assertValidHash/assertValidFilename guards added for #13/#14).
- **Impact:** A compromised/abused renderer (or a malicious markdown-driven XSS, mitigated but not eliminated by CSP) can write an attacker-controlled .md file (arbitrary content; filename constrained to the validateEntityName charset, fixed .md / SKILL.md suffix, forced under a .claude/agents|skills infix) to ANY directory on the filesystem, e.g. projectPath='/tmp/evil' producing /tmp/evil/.claude/agents/<name>.md. This is the 'writing outside ~/.claude' / 'absolute-path injection from renderer-supplied input' the security invariant forbids, and it escapes $HOME entirely — unlike markdownFile:* which at least requires under-home.
- **Fix:** Validate projectPath in both writers (and/or in the IPC handlers) before constructing the base dir: require it to be an absolute, existing directory and confine the final write under an allowed root. Either restrict to under os.homedir()/CLAUDE_DIR with an explicit assertSafeWritePath({requireUnderHome:true}) on the resulting filePath, or resolve projectPath and assertWithin(home, projectPath). At minimum, assertWithin must be anchored on a trusted base (home), not on a base computed from the untrusted input.

#### 3. CRLF frontmatter is silently dropped by both frontmatter regexes

- **Severity:** 🟠 High · **Category:** correctness · **Cluster:** `readers-misc`
- **Location:** `electron/modules/frontmatter.ts:18`
- **Problem:** Both the shared parseFrontmatter regex and the standalone copy in rules-reader.ts require LF immediately after the opening --- and before the closing ---. A CRLF-authored file (---\r\n...\r\n---\r\n) does not match, so parseFrontmatter returns {frontmatter:{}, body:<entire file including the YAML>}. No code path normalizes \r before parsing.
- **Impact:** On Windows (an officially supported, merged platform per project memory #51) every CLAUDE.md, SKILL.md, agent .md and memory topic edited with a CRLF editor loses ALL frontmatter: agents/skills show no name/description and report bogus missingRequired:['name','description'] (agents-reader.ts:118); memory topics fall back to filename-prefix type inference and lose originSessionId; rule files lose their paths and are treated as always-applied instead of path-scoped. The YAML also leaks into the rendered body.
- **Fix:** Normalize line endings once at the top of parseFrontmatter (content = content.replace(/\r\n/g, '\n')) before matching, or make the fences CRLF-tolerant (/^---\r?\n([\s\S]*?)\r?\n---/). Apply the same fix to rules-reader.ts:13, or better, route rules-reader through the shared parseFrontmatter + getStringArray('paths') so there is one chokepoint.

#### 4. Plan file content is read from an unconfined absolute path taken verbatim from the transcript (arbitrary file read, escapes the ~/.claude invariant)

- **Severity:** 🟠 High · **Category:** security · **Cluster:** `session-parsing`
- **Location:** `electron/modules/plans-reader.ts:69-71,100-120`
- **Problem:** extractPlanRefs() pulls `att.planFilePath` straight out of each `plan_mode`/`plan_mode_exit` attachment line in a session .jsonl (lines 69-71) with no validation beyond `typeof === 'string'`. toPlan() then does `readFileSync(ref.filePath, 'utf-8')` on that exact string (line 104) with NO confinement — it is never checked to live under ~/.claude/plans or even under ~/.claude. The whole flow is live: `plans:getByProject` -> getProjectPlans() -> dedupeRefs(extractPlanRefs(file)).map(toPlan). A .jsonl that lands in ~/.claude/projects/<hash>/ (a synced/shared transcript, a repo-committed transcript, or a hand-crafted file) can therefore set `planFilePath` to any absolute path on disk (e.g. "/etc/passwd", "~/.aws/credentials", a project secrets file). The contents are read and returned to the renderer, which renders them in PlansSection/PlanDetailView (plan.content). This breaks the project's stated invariant that filesystem access is confined to ~/.claude — the READ escapes even the home boundary. It compounds on the write side: PlanDetailView feeds the same untrusted plan.filePath back into markdownFile:write / markdownFile:delete (PlanDetailView.tsx:60-61), and assertSafeWritePath only enforces requireUnderHome + an `.md` suffix (electron/main.ts:124-146), so a crafted planFilePath ending in `.md` anywhere under $HOME can be overwritten or deleted via the Save/Delete buttons.
- **Impact:** Arbitrary file-content disclosure: any file on the machine readable by the user can be surfaced in the ClaudeLens UI via a poisoned/shared transcript placed under ~/.claude/projects/, and any `.md`-suffixed file under the user's home can be overwritten/deleted through the Plan detail view. Violates the security invariant that all reads/writes/deletes stay inside ~/.claude. The read needs no user action beyond opening the Plans tab; the write/delete needs a click on Save/Delete. Requires attacker-controlled local transcript content (not remotely triggerable).
- **Fix:** Confine the plan path at the reader. In toPlan()/extractPlanRefs, resolve(ref.filePath) and require it to start with PLANS_DIR (~/.claude/plans) + path separator before readFileSync; drop or mark-missing any ref that escapes (the UI already states plans are 'Stored globally in ~/.claude/plans'). Pass PLANS_DIR into getProjectPlans (as tasks-reader already takes its dir) rather than relying on the renderer. Separately, tighten the write side: have markdownFile:write/delete for plans use requireUnder: PLANS_DIR instead of the broad requireUnderHome, so a stray planFilePath can't target arbitrary .md files under home.

## 🟡 Medium priority (13)

#### 1. sendMessage passes unvalidated sessionId to the SDK as `resume` (no isValidSessionId guard)

- **Severity:** 🟡 Medium · **Category:** security · **Cluster:** `chat-lifecycle`
- **Location:** `electron/main.ts:1100-1134`
- **Problem:** `sessions:sendMessage` only checks `if (!sessionId)` (main.ts:1100) and then forwards `sessionId` straight into `launchSession({ resume: sessionId, ... })` (main.ts:1129), which the Agent SDK uses as the transcript identifier under `~/.claude/projects/<hash>/<id>.jsonl` (chat-runner.ts:219 -> sdk.query resume option). There is no `isValidSessionId()` UUID check, even though the sibling `terminal:create` handler validates exactly this kind of value before use (main.ts:1229) and `electron/utils.ts:44` exists for precisely this purpose. The id crosses the IPC boundary as an arbitrary renderer-supplied string.
- **Impact:** A malformed or path-bearing `sessionId` is handed to the SDK's resume/session-file resolution with no validation, inconsistent with the project's stated invariant that ids are validated before being used in a file/command path. In normal use the renderer derives the id from on-disk filenames so it is well-formed, which limits exploitability, but the boundary is unguarded and inconsistent with the rest of the codebase (terminal:create validates the same shape).
- **Fix:** Mirror the terminal handler: add `if (!isValidSessionId(sessionId)) return err(new Error('Invalid session id.'));` right after the empty check in `sessions:sendMessage`. `isValidSessionId` is already imported in main.ts (line 59).

#### 2. Optimistic prompt bubble + frozen transcript stick forever when a turn ends without growing the persisted transcript

- **Severity:** 🟡 Medium · **Category:** bug · **Cluster:** `chat-view-state`
- **Location:** `src/components/project/chat/ChatView.tsx:947-979`
- **Problem:** The reconcile effect that tears down the in-flight live turn is gated solely on disk growth: `if ((messages?.length ?? 0) > pendingBaseCount.current)` (L950), where pendingBaseCount is captured at send time (L1532). A turn that the SDK starts but that dies on a fatal stream error before persisting anything writes nothing to disk; per the chat-runner/main contract the main still emits a final `chatDone` (main.ts L1059-1068), so the composer sets sending=false and ChatView's `streaming` goes false, but `onSendFailed` is NOT fired (onChatError only sets errorText). In that case streaming is false and pendingUser is non-null, yet messages.length never exceeds pendingBaseCount, so the effect body never runs. (Note: the reviewer's secondary 'only artifact is the No response requested. placeholder' case does NOT apply — the command-card user line is persisted and counted.)
- **Impact:** The optimistic user bubble (`__pending_user__`) and the frozen pre-turn snapshot remain rendered until the user sends another message (which re-seeds the state) or leaves the view (which remounts ChatView). Display is read from frozenMessages while pendingUser !== null, so background file-watcher refetches can't clear it. The user sees a 'sent' prompt that produced nothing and a transcript frozen on a stale snapshot, with no automatic recovery — but only on the narrow fatal-error-before-disk-write path.
- **Fix:** Don't rely solely on disk growth to end the live turn. Add a composer→parent 'turn ended' signal on onChatDone (e.g. onTurnEnded) and, in ChatView, when `!streaming && pendingUser !== null`, reconcile after a short grace/refetch even if the length didn't grow — fall through to `setPendingUser(null); setFrozenMessages(null); setLiveMessages([])` once the turn is known-ended, regardless of the `>` comparison. Use a 'turn ended' flag as the primary gate rather than a length delta.

#### 3. markdownFile:write / markdownFile:delete confined to $HOME, not ~/.claude — arbitrary .md overwrite/delete anywhere under home

- **Severity:** 🟡 Medium · **Category:** security · **Cluster:** `filesystem-security`
- **Location:** `electron/main.ts:396-428`
- **Problem:** Both handlers guard renderer-supplied filePath only with assertSafeWritePath(filePath, { requireUnderHome: true }). requireUnderHome checks resolved.startsWith(os.homedir() + sep) (main.ts:128-133) — i.e. anywhere under $HOME — and the basename check only requires a .md suffix (main.ts:143-145). The security invariant states all writes/deletes MUST be confined to ~/.claude. These handlers are far broader: any *.md path under $HOME is accepted. markdownFile:write then writeFileSync's renderer-controlled content (and mkdirs missing parents); markdownFile:delete rmSync's the target. Path traversal via '..' is blocked (resolve() collapses it before the under-home check), so this is a scope problem, not a traversal problem: legitimate-looking absolute .md paths anywhere under home (e.g. ~/Projects/app/README.md) all pass. Note: commit 69c4248 made this broadening deliberate (to support project-scoped agents/skills under {projectPath}/.claude), so the divergence is from the ~/.claude invariant specifically.
- **Impact:** A renderer that can choose filePath (or a future caller that passes a path not derived from a trusted reader) can overwrite or delete any EXISTING .md-suffixed file in the user's home tree, well outside ~/.claude — clobbering project READMEs, docs, or notes with attacker content, or deleting them. Non-.md files are not reachable (the .md filter), so blast radius is narrower than finding [1]. Still violates the stated ~/.claude confinement invariant and widens blast radius beyond the agents/skills/plans use cases the requireUnderHome relaxation was intended for.
- **Fix:** Tighten the confinement to the actual allowed roots. For global agents/skills/CLAUDE.md/plans use requireUnder: CLAUDE_DIR. For project-scoped agents/skills (which live at {projectRealPath}/.claude/...), pass the project's realPath and use requireUnder that realPath's .claude subtree (or accept a (projectRealPath, relativePath) pair the renderer can't point elsewhere) rather than a blanket under-$HOME check with a .md filter.

#### 4. Path guards are purely lexical — no symlink resolution, so a planted symlink escapes ~/.claude/$HOME

- **Severity:** 🟡 Medium · **Category:** security · **Cluster:** `filesystem-security`
- **Location:** `electron/utils.ts:32-38`
- **Problem:** Every containment check in the cluster — assertWithin (utils.ts:32-38), assertSafeWritePath (main.ts:124-147), deleteSessionArtifacts (session-deleter.ts:165-176), assertValidHash (main.ts:71-83) — relies solely on path.resolve(), which normalizes '.'/'..' lexically but does NOT follow symlinks (no realpathSync/lstat anywhere; grep for realpath/lstat/isSymbolicLink returns nothing). So if any symlink exists inside the supposedly-confined tree (e.g. ~/.claude/projects/-X/memory -> /etc, or a session sidecar dir symlinked out), a path that is lexically under the base passes the guard while the real write/delete target is outside it. createTopic/updateTopic/deleteTopic (memory-writer.ts), executeMerge's writes, and deleteSessionArtifacts' rmSync/unlinkSync would all follow such a link. Note deleteSessionArtifacts uses statSync (not lstatSync) at line 182, so a symlinked directory is followed by the recursive rmSync.
- **Impact:** Defense-in-depth gap: an attacker (or a malicious project-history folder shipped to the user) that can place a symlink inside ~/.claude turns an in-scope write/delete into an out-of-scope one — e.g. deleteSessionArtifacts rmSync(resolved, {recursive:true,force:true}) through a symlinked directory could delete files outside ~/.claude. Lower likelihood than findings 1-2 (needs a pre-existing planted symlink) but it defeats the stated containment guarantee.
- **Fix:** After resolve(), also realpathSync the longest existing ancestor of the target (the target itself may not exist yet) and re-check that the real path is still under the canonical realpath of the base. For deletes, use lstatSync/realpathSync on the target before rm/unlink (and prefer lstatSync over statSync so a symlinked dir is not recursively removed through). Apply consistently in assertWithin and assertSafeWritePath so all write sites inherit it.

#### 5. Merge rollback can delete a pre-existing destination file instead of restoring it (only source is backed up)

- **Severity:** 🟡 Medium · **Category:** correctness · **Cluster:** `filesystem-security`
- **Location:** `electron/modules/duplicate-merge-executor.ts:159-202`
- **Problem:** executeMerge backs up only the source dir (cpSync sourceDir -> backupPath, line 146; the dest is not backed up — only MEMORY.md's text is captured at line 157). Session moves use writeAtomicPreservingMtime which does renameSync(tmp, destPath) (line 73) — an unconditional overwrite of destPath if it exists. Collision avoidance comes from computeMergePlan's targetName (filename when not colliding); executeMerge recomputes the plan once at line 133 but there is still a TOCTOU window between that recompute and each rename where a file can appear at destPath (the watcher is paused for ClaudeLens' own writes, but the terminal claude CLI or another process can write into destDir concurrently). If such a dest file is overwritten and then any later step throws, rollback() iterates createdInDest in reverse and rmSync's each destPath (lines 160-162) — deleting the file that was overwritten rather than restoring it, because the destination was never backed up. Memory copyFileSync into destMemDir (line 233) has the same shape (a dest topic appearing post-plan is overwritten then removed on rollback).
- **Impact:** In the (narrow) case of a concurrent write into the destination folder during a merge that subsequently fails, the rollback compounds the damage: a legitimate destination transcript/topic that existed before the merge is deleted and not recoverable from the source backup. State ends up worse than 'no merge'.
- **Fix:** Before overwriting, assert the dest path does not already exist (writeAtomicPreservingMtime / copyFileSync should fail-closed if destPath exists when the plan said it shouldn't — e.g. rename/open the tmp target with wx semantics, or existsSync-check destPath immediately before rename and abort the merge if present). Alternatively back up the destination dir too, and have rollback restore overwritten dest files from that backup rather than blindly rmSync'ing createdInDest.

#### 6. Live 1s uptime tick re-renders the entire ProjectView subtree, including the full (unmemoized) session list

- **Severity:** 🟡 Medium · **Category:** performance · **Cluster:** `heavy-components-perf`
- **Location:** `src/components/project/overview/ProjectOverviewContent.tsx:263-282, 1178-1344`
- **Problem:** liveSec is component state on ProjectView itself, updated every 1000ms by setInterval whenever a live session exists for the project (livePid !== undefined). Each tick re-renders the whole ProjectView function body and all its children, because none of the heavy children are memoized: SessionRows, MemoryRows, PinnedSessionsSection are plain function components with no React.memo. In the sessions section SessionRows renders the entire visibleSessions array (not sliced — a busy project can have hundreds of .jsonl sessions), and for each row it calls isPinned, tagsForSession, modelFamily, builds a tag list and 3 buttons. So once per second, with a terminal open on the sessions tab, the app re-builds the full session list DOM tree purely to advance an uptime string in one Live card.
- **Impact:** With a live terminal session attached to the project and the Sessions section open on a large history, the renderer does a full reconciliation of the entire session list every second — visible jank / wasted CPU and battery while the user is just reading. The overview section is lighter (sessions sliced to 5) but Memory/CLAUDE.md/config-strip still re-render each second too. Gated on a live session existing for this project, so it does not fire on idle projects.
- **Fix:** Isolate the ticking value: move the live-uptime interval+display into a small dedicated <LiveUptime startedAt={liveStartedAt} pid={livePid}/> child that owns its own liveSec state, so only that card re-renders each second. Same for nowMs (extract the stats band, or push nowMs into the stats subtree). Additionally wrap SessionRows/MemoryRows in React.memo so unrelated parent re-renders don't rebuild the list.

#### 7. Undebounced data:changed triggers full transcript re-read/parse storm during a live chat turn

- **Severity:** 🟡 Medium · **Category:** performance · **Cluster:** `ipc-hooks`
- **Location:** `src/hooks/useIPC.ts:684-708`
- **Problem:** useDataChangedRefetch() subscribes once (App.tsx) and, with NO debounce, invalidates ~16 query keys on every onDataChanged callback. The main process emits 'data:changed' undebounced on every chokidar add/change/unlink across PROJECTS_DIR/TASKS_DIR/PLANS_DIR (electron/main.ts:1400-1407 `notify` sends directly, unlike the sessions-registry watcher which debounces at 400ms). During a live chat turn the transcript .jsonl is appended continuously. Line 694 invalidates ['sessions:chat'], the ACTIVE query an open ChatView observes (ChatView.tsx:844 useChatSession), and React Query refetches active observers on invalidate, so each event re-runs sessions:getChat -> readChatSession, a synchronous readFileSync(...).split('\n') + per-line JSON.parse over the ENTIRE file (session-reader.ts:141-145). Cost is O(file size) per event, repeated per turn on a growing file, alongside the parallel cost/sessions/tasks/plans re-reads.
- **Impact:** On longer sessions a single chat turn triggers repeated full-file reads/parses on the main process (synchronous fs + JSON.parse), causing CPU/GC churn and IPC traffic while the user is actively chatting. ChatView already ignores these mid-stream refetches for DISPLAY (it renders from the SDK stream until the turn closes, ChatView.tsx:893-900), so the refetched data is discarded until reconcile — the work is wasted. Magnitude is bounded by main-process execution and typical JSONL sizes, so it is a CPU/efficiency issue rather than a user-visible UI freeze.
- **Fix:** Debounce the handler in useDataChangedRefetch (coalesce bursts with a ~150-300ms trailing timer, cleared on unmount) so a burst of file events collapses into one invalidation pass. Alternatively/additionally debounce the emit side in main.ts `notify` the same way the sessions-registry watcher already does.

#### 8. Watcher refetch never invalidates sessions:subagents / sessions:subagentTranscript — open session view goes stale

- **Severity:** 🟡 Medium · **Category:** correctness · **Cluster:** `ipc-hooks`
- **Location:** `src/hooks/useIPC.ts:688-705`
- **Problem:** The invalidation set in useDataChangedRefetch (lines 689-704) lists memory/cost/sessions:project/sessions:chat/claudeMd/rules/tasks/plans/skills/agents/mcp but omits ['sessions:subagents'] and ['sessions:subagentTranscript']. An open ChatView consumes useSessionSubagents (ChatView.tsx:845) for the agent dock + sub-agent list, and SubagentTranscriptPanel consumes useSubagentTranscript (ChatView.tsx:1398). Sub-agent transcripts are written by a live session under {PROJECTS_DIR}/<hash>/<sessionId>/subagents/agent-*.jsonl. When Claude spawns/continues sub-agents during a turn neither subagent query is invalidated by the watcher path, and no mutation backstops them (unlike sessions:chat, which IS in the set). The only refresh is a component remount.
- **Impact:** While a session is open and actively running sub-agents, the agent dock and any open sub-agent transcript do not update — newly dispatched sub-agents don't appear, and an open transcript stops growing — until the user navigates away and back. (The chokidar depth:3 root at PROJECTS_DIR does not directly reach the 4th-segment agent-*.jsonl, but the parent session .jsonl changing in the same turn already fires data:changed, so adding the keys fixes the staleness either way.)

#### 9. sessions:sendMessage / startMessage lack an outer try/catch, violating the {data,error} IPC invariant

- **Severity:** 🟡 Medium · **Category:** bug · **Cluster:** `ipc-watchers`
- **Location:** `electron/main.ts:1084-1138, 1144-1172`
- **Problem:** Unlike essentially every other handler in main.ts, the two chat-send handlers have no outer try/catch. Their bodies run `await import('fs')`, `statSync(realPath)`, and `message.trim()` directly. `message.trim()` (1101/1153) is evaluated before any type guard on `message`; if a caller passes a non-string (preload types it `string`, but a stale build or future caller could violate that) it throws a raw `TypeError: message.trim is not a function`, and the IPC invoke promise rejects instead of resolving to `{data:null,error:...}`. `await import('fs')` failing has the same effect. Every neighbouring handler (e.g. sessions:getChat at 594) wraps its body in `try { ... } catch (e) { return err(e) }` precisely to honor the contract.
- **Impact:** Breaks the documented IPC invariant ('every handler returns { data, error }') for the highest-traffic write path (send/start chat). A malformed/undefined message rejects the invoke; the renderer's own try/catch in ChatComposer.doSend does catch it and shows the raw TypeError text as an error toast (so no unhandled rejection and no stuck composer), but the error message is a programmer-facing 'message.trim is not a function' rather than a clean 'Cannot send an empty message.'
- **Fix:** Wrap both handler bodies in try/catch returning `err(e)`, exactly like sendMessage's siblings, and guard the argument up front: `if (typeof message !== 'string' || !message.trim()) return err(new Error('Cannot send an empty message.'))` before calling `.trim()`.

#### 10. Live-session registry dir (watch + readActiveSessions) ignores CLAUDE_CONFIG_DIR

- **Severity:** 🟡 Medium · **Category:** correctness · **Cluster:** `ipc-watchers`
- **Location:** `electron/modules/sessions-registry-reader.ts:31-33, 83`
- **Problem:** defaultSessionsDir() hardcodes `join(homedir(), '.claude', 'sessions')`, and readActiveSessions defaults `dir` to it. Everything else derives paths from CLAUDE_DIR (utils.ts:6 = process.env.CLAUDE_CONFIG_DIR ?? ~/.claude). So when a user relocates their Claude data dir via CLAUDE_CONFIG_DIR, both the chokidar sessions watch (main.ts:1413) and the live:getActiveSessions reader point at ~/.claude/sessions, the wrong directory.
- **Impact:** For any user who set CLAUDE_CONFIG_DIR, the registry-backed active-sessions data is lost: the dedicated live:activeSessions push never fires (watched dir is absent), and the reader degrades to the process-scanner fallback (coarse: no sessionId/status/waitingFor, no live push, [] on Windows). Silent feature degradation with no error shown.
- **Fix:** Derive the sessions dir from the same root as the rest of the app: compute `process.env.CLAUDE_CONFIG_DIR ?? join(homedir(), '.claude')` inside defaultSessionsDir (or import CLAUDE_DIR from utils and use join(CLAUDE_DIR, 'sessions')). Keep the options.dir override for tests.

#### 11. Concurrent startLiveMonitor calls leak chokidar watchers

- **Severity:** 🟡 Medium · **Category:** race · **Cluster:** `live-monitoring`
- **Location:** `electron/modules/live-monitor.ts:41-89`
- **Problem:** startLiveMonitor() calls stopLiveMonitor() at the top (L46) but performs `await import('chokidar')` (L74) — and `await glob(...)` (L62) when there's no exact sessionId — BEFORE assigning the module-global `state` at L77. The renderer effect (src/tabs/LiveMonitor.tsx:118-127) re-runs startWatch whenever liveSessionId changes, with a cleanup that calls stopWatch. If two start/stop sequences interleave across the awaits, call B's stopLiveMonitor closes only the current state.watcher while call A's watcher hasn't been created/assigned yet; A then assigns its watcher, B overwrites it, and A's watcher is leaked.
- **Impact:** Orphaned chokidar FSWatchers can accumulate on the live transcript file when the active session id flips while a start is in-flight (registry heartbeat picks a different session, user switches sessions, or React re-mounts). Each orphan keeps an open fs.watch handle and a 'change' listener that still fires parseJsonlLine -> onEvent into event.sender, leaking memory and emitting duplicate/ghost live events. Bounded by how often a flip races an in-flight start, not unbounded per flip.
- **Fix:** Serialize start/stop with a generation token: capture a local counter at entry, and after the awaits, if a newer start has superseded this one (or `state` already points elsewhere), close the just-created watcher and return instead of assigning. Alternatively create the watcher before any await (or await an in-flight close() promise), then guard the assignment.

#### 12. Dead session shown as live (and tailed) on PID reuse; heartbeat never used to age out stale entries

- **Severity:** 🟡 Medium · **Category:** correctness · **Cluster:** `live-monitoring`
- **Location:** `electron/modules/sessions-registry-reader.ts:36-44,93-105`
- **Problem:** isPidAlive() only checks that SOME process with that pid exists (process.kill(pid,0), with EPERM treated as alive); it cannot tell whether that pid is still the Claude process that wrote the file. A crashed Claude session leaves its ~/.claude/sessions/<pid>.json behind. On macOS/Linux pids are recycled, so once the OS reassigns the dead session's pid to any unrelated process, isPidAlive returns true and the stale entry survives the filter at L98 and is reported as an ActiveSession. The updatedAt heartbeat (parsed at L69) is never compared against Date.now(), so there is no freshness gate.
- **Impact:** The Live view can list a session that is no longer running, with stale status/cwd. The renderer feeds that stale sessionId into live:startWatch (LiveMonitor.tsx:116-120), so the monitor tails a long-dead session's transcript believing it is live. Occurs when a Claude crash orphaned a registry file whose pid later gets reused.
- **Fix:** Add a heartbeat staleness gate alongside the pid probe: drop entries whose updatedAt is older than a small multiple of the known heartbeat interval (e.g. > 30-60s). This is the registry's own liveness signal and is immune to pid reuse. Keep the pid probe for the no-updatedAt (older CLI) case.

#### 13. A single null/non-object project entry in .claude.json zeroes out the entire cloud MCP panel

- **Severity:** 🟡 Medium · **Category:** bug · **Cluster:** `readers-misc`
- **Location:** `electron/modules/mcp-reader.ts:39-48`
- **Problem:** The project loop dereferences proj.disabledMcpServers for every value of data.projects. If any entry's value is null (or otherwise not an object), the access throws. That throw is caught by the broad try/catch (lines 33-48) whose handler is empty, so cloudConnected and projectStates are both discarded and stay empty.
- **Impact:** One malformed/null project key (Claude Code's ~/.claude.json is an undocumented, frequently-rewritten internal file) makes the whole cloud-MCP grid render zero servers — the UI shows 'active in N of M projects' from enabledInProjects (McpServerGrid.tsx:110), so users see an empty/blank MCP view with no error. The blast radius is disproportionate to the cause.
- **Fix:** Guard each entry: if (proj && typeof proj === 'object' && Array.isArray(proj.disabledMcpServers) && proj.disabledMcpServers.length) { projectStates.push({ path, disabled: proj.disabledMcpServers }); } else { projectStates.push({ path, disabled: [] }); }, skipping/defaulting non-object entries instead of letting one throw collapse the whole read.

## Refuted by verification (3)

Listed for transparency — the review agent flagged these but the skeptic traced the code and refuted them. Do **not** action these.

- **ChatView is not keyed by session id, so live-turn / pinned state bleeds across session switches** (`src/components/project/chat/ChatView.tsx:815-916`)
  - _Why refuted:_ REFUTED. The reviewer looked only for a `key` directly on `<ChatView>` (ProjectOverview.tsx L322-332, indeed absent) and missed the wrapping boundary. The `chat` case is rendered by renderDeepView() (switch at ProjectOverview.tsx L254-255), and `chat` is NOT in CORE_PROJECT_VIEWS (L61), so isEditorialCore is false and the deep-view branch at L390 is taken. That branch wraps the subtree in `<ErrorBoundary key={JSON.stringify(view)}>{renderDeepView()}</ErrorBoundary>` (L394). For a chat, `view` = { type: 'chat', project, session, from }, so JSON.stringify(view) changes whenever `session` changes — a React key change forces a FULL unmount/remount of the ChatView subtree. Therefore navigating session A→B (from agents-live, a Tasks/Plans header, or Sessions) reinitializes ALL of ChatView's useState (pendingUser, frozenMessages, pinnedSlash L901/904/915, activeTurn L924, turnRefs L925, viewMode, etc.) on the fresh mount, and unmounts the composer (firing its mount-only endChat, ChatComposer.tsx L334-338, disposing session A's SDK session). The premise 'reuses the same ChatView instance with a new session prop' is false; the proposed fix (key ChatView by session id) is already effectively in place one level up. Confirmed there is no useEffect keyed on session.filename inside ChatView (grep shows session.filename only feeds hooks/sessionId, never a reset) — but that absence is harmless precisely because the higher key remounts the whole subtree. Left at low severity to flag the latent fragility: the protection relies on JSON.stringify(view) differing per session; a future refactor that drops that key or moves chat into CORE_PROJECT_VIEWS would reintroduce the bleed.
- **Scroll-spy IntersectionObserver re-subscribes only on minimapItems identity, not when turnRefs are repopulated** (`src/components/project/chat/ChatView.tsx:1169-1183`)
  - _Why refuted:_ REFUTED. The effect deps are [minimapItems, viewMode, feedRef] (L1183) and it observes the turnRefs.current snapshot at run time (L1181). The reviewer's premise — that turnRefs can gain a minimap-relevant node WITHOUT minimapItems changing identity, e.g. 'React reuses keys after reconcile without changing the derived minimapItems array' — does not hold. minimapItems is a useMemo chain off processed: displayMessages (L988-1007, depends on liveMessages/frozenMessages/messages) → processed = buildProcessedMessages(displayMessages) (L1010) → descriptors (L1049) → visibleItems (L1067) → minimapItems (L1076). Every streamed message during a live turn produces a NEW displayMessages array → new processed → new minimapItems identity, so the effect re-runs on every live-turn growth and re-observes the freshly-registered refs (refs fire during commit, the effect runs after commit, so the new nodes are present when it re-runs). At reconcile, processed is rebuilt from the disk read (new array identity) → minimapItems changes again → effect re-runs. The only node never observed is the trailing LiveTurn (L1496-1499), which by design has no data-n and no innerRef={setTurnRef} (LiveTurn component L755-796 renders no data-n) — it is the in-flight turn and is intentionally not a navigable minimap dot. So there is no realistic case where activeTurn fails to track a newly-rendered NAVIGABLE turn due to a missed re-subscribe. The genuine residual issue (the effect also observes STALE detached nodes left in turnRefs) is the Finding-3 accumulation concern, not a re-subscription gap, and is benign. Verdict false_positive; any remaining nit is cosmetic and already covered by Finding 3.
- **tagsForSession/tagsForMemory callback identity is unstable for projects with no tags, defeating the visibleSessions/visibleMemTopics memos and re-running list filters** (`src/hooks/useNamespacedTags.ts:81-83, 161-164`)
  - _Why refuted:_ The identity-instability half of the claim is real but the described HARM cannot occur. Verified: root comes from usePersistentState's `value`, which is React state (usePersistentState.ts:71) — root keeps a STABLE identity across renders unless setValue fires (commit or a 'storage'/event sync). In the no-tags case root[projectHash] is undefined, so line 81 calls emptyProject() (a useCallback that returns a FRESH object each call), making `project` fresh every render; itemsOf(project) (line 83) then returns the fresh inner {} object; tagsFor = useCallback(..., [items]) (161-164) therefore changes identity every render. So far the reviewer is correct. BUT the consumer guards make this harmless: visibleSessions (ProjectOverviewContent 334-337) does `if (!activeTag) return sessions` BEFORE touching tagsForSession, and activeTag = tagFilter && projectTags.some(...) ? ... : null — with NO tags, projectTags is empty, so activeTag is ALWAYS null, so the memo always hits the early `return sessions` and the .filter() is NEVER executed. The two conditions are mutually exclusive: filtering requires an active tag, which requires tags to exist, which makes root[projectHash] defined and tagsForSession STABLE. So in the no-tags case the memo callback re-runs but only does a property-access + early return (a no-op returning the same stable `sessions` ref — no downstream re-render, no filtering); in the has-tags case the callback is stable and the memo is not defeated. visibleMemTopics (347-350) has the identical guard and conclusion. Also, SessionRows (1192-1202) calls useSessionTags itself and invokes tagsForSession directly in render (line 1212), not inside any memo, so callback stability is irrelevant there. The headline impact ('redundant array filtering over the full session list every render / every 1s tick') does not happen.
